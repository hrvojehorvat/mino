## 2026-09-02 — Phase 1 implementation: finger-tapping MVP

- **Casing correction (important, caught during plan review, not by me):** the initial Phase 1 plan drafted the Prisma schema in snake_case to match `data-model.md`/`testing.md`'s field-name tables literally. The user correctly rejected this — those docs were written before any real schema existed and were themselves wrong, not a source of truth to be matched. Since this is a pure TypeScript stack end-to-end (RN mobile talking to a NestJS backend it owns), the fix was to make everything camelCase (Prisma fields, `shared-types` wire contract, DTOs) and PascalCase for enum members, then correct the docs to match the real, idiomatic schema. Lesson: when a doc and an idiomatic-convention decision conflict, prefer the convention and fix the doc — don't contort code to match a doc that predates the decision.
- Implemented and verified end-to-end: Prisma schema (`User`/`TestSession`/`RawEvent`, camelCase fields + PascalCase enums), `PrismaService`/`PrismaModule`, `POST /sessions` ingestion endpoint with `class-validator` DTOs + a global `ValidationPipe` (`whitelist`, `forbidNonWhitelisted`, `transform`), service-level physical-plausibility checks (event count vs. session duration, `tMs` bound), and a `sessions.e2e-spec.ts` integration test suite (5 tests) run against a dedicated `mino_test` Postgres database via `dotenv-cli` + `prisma migrate deploy`.
- Mobile: `TappingScreen.tsx` captures touch down/up events with `performance.now()`-relative timestamps (chosen specifically to avoid iOS/Android native-timestamp epoch differences), persists a device UUID via `expo-crypto` + `AsyncStorage` as the MVP's non-auth identity, and submits the batch to the API on session completion. Verified by type-checking cleanly and bundling successfully for web (241 modules, no errors) — actually tapping through a live session on a simulator/device is a manual step, not something I can automate from here.
- RN's `GestureResponderEvent.nativeEvent.identifier` (touch pointer id) is typed as `string` in this React Native version, not `number` — had to `Number(...)`-convert it before storing as `pointerId`.
- Metro (RN's bundler) resolves imports without file extensions; the NestJS backend's `nodenext` ESM setup requires explicit `.js` extensions on relative imports. Mixed these up once while scaffolding mobile files — worth remembering these are two different module-resolution worlds within the same monorepo.

## 2026-09-03 — Phase 2: remaining test types (Reaction Time through Guided Movement)

- **Continuous-sensor storage resolved as JSONB, not row-per-sample.** New `SensorSession` table (one row per session, `samples: Json`) for accelerometer/gyroscope streams, kept behind an isolated `SensorSessionsService.storeSamples()` so a later migration to blob storage stays localized to one method — the API contract and mobile client never need to change. See `decisions/0003-raw-event-storage-model.md` (now resolved).
- **Hook-extraction pattern, applied twice this phase:** extract shared screen logic at the *second* occurrence, not preemptively. `useTestSession` (session state machine: idle/running/submitting/done/error, device-id, submission) was pulled out of `TappingScreen` when Reaction Time needed the same flow; `useMotionSensors` (accelerometer+gyroscope subscribe/availability-check) was pulled out of `PhoneStabilityScreen` when Guided Movement needed the identical sensor-capture logic. Both extractions happened exactly when a second consumer appeared, not before.
- **`expo-sensors`' web shim is unreliable — don't trust `isAvailableAsync()` on web.** It can resolve `true` on desktop browsers even though the underlying native module then throws (`addListener is not a function`) or silently no-ops (`WARN expo-sensors: setUpdateInterval() is not supported on web`, followed by a zero-sample submission failure). Fix: gate on `Platform.OS === 'web'` first and treat web as always-unavailable for sensor-based tests, skipping the async check entirely on that platform. Mino is fundamentally a mobile app — web here is only this project's own build-verification tool (`expo export --platform web`), not a target end-user platform, so this tradeoff is fine.
- **Sensor-required tests should hard-gate, not gracefully degrade.** First attempt at Phone Stability silently fell back to accelerometer-only when the gyroscope was missing; the user explicitly rejected this in favor of disabling the Start button up front with an explanatory message when sensors aren't available, requiring a different device rather than recording a degraded/partial session. Applied to both Phone Stability and Guided Movement via `useMotionSensors`'s `checking`/`available`/`unavailable` status.
- **Precise symptom description was the key diagnostic signal for a "blank screen" bug.** "Black screen" was ambiguous (crash? native module issue?); "white screen, empty, but the back button is still visible" pinpointed that the parent shell rendered fine and only the child failed to render — which turned out to be a missing JSX conditional line in `App.tsx` (the test's entry in the `TESTS` array and import existed, but no `{selectedTest === 'x' && <Screen />}` line matched it), not a sensor/native-module issue at all. Added an `ErrorBoundary` around test screens afterward so future render crashes surface an on-screen message instead of a blank one.
- **Don't rely on a framework's default body-size limit for real payloads.** Express defaults to a 100kb JSON body limit; a real-device Phone Stability session (~15s at ~50Hz) produced a ~124KB payload, exceeding it and failing with `PayloadTooLargeError` — before the request ever reached our own DTO-level array-size validation. The original transport-decision estimate (`decisions/0004-batched-http-transport.md`) had guessed "well under 100KB," which was wrong. Fixed by setting `app.use(json({ limit: '5mb' }))` explicitly in `main.ts`. Lesson: size the server's body limit explicitly and verify against a real payload rather than trusting a framework default or an un-measured estimate.

## 2026-09-03 — Phase 3: ML pipeline v1 (feature math for all six test types)

- **Synthetic unit tests alone missed two real bugs — spot-checking against real dev-DB data caught both.** Both bugs passed every hand-computed synthetic test and only showed up once the poller ran against actual captured phone sessions:
  - Finger Tapping paired `TouchDown`/`TouchUp` events positionally (`zip(downs, ups)`). A real session had a dropped `TouchUp` (a `TouchDown` with no matching `TouchUp` before the next `TouchDown`), which silently misaligned every duration after that point (~1398ms mean instead of a plausible ~133ms). Fixed with a stateful single-pass pairing loop that only advances on a matched `TouchUp`, and added a regression test for exactly this shape.
  - Phone Stability's "shaking frequency" was computed by taking the periodogram of the combined 3-axis magnitude signal. For a single-axis oscillation this rectifies the signal (sqrt of a squared sine wave), which doubles its apparent frequency — a real synthetic-sine-wave test caught this directly (expected 2Hz, got 4Hz). Fixed by summing each axis's own power spectrum instead of the periodogram of their combined magnitude (power adds linearly across axes; time-domain magnitude does not).
  - Lesson: for any signal-processing/timing code, treat "passes synthetic unit tests" as necessary but not sufficient — always run it against at least one real captured session per test type before calling a feature module done. Both bugs were invisible to made-up fixtures because the fixtures didn't happen to reproduce the real data's actual shape (a dropped event; a single-axis rather than multi-axis oscillation).
- **`modelVersion` is bumped when the math changes, never when just adding a new test type's math for the first time.** Old `MLResult` rows are kept as history under their original version (unique on `(sessionId, modelId, modelVersion)`); a version bump adds new rows alongside old ones rather than overwriting. During local dev-only verification, a bug fix made an already-computed local version's rows stale — since that data was purely local scratch (not shipped/committed anywhere), the fix was to delete and recompute under the same version rather than bump again, which would only matter for already-shipped data.
- **Explicit if/elif dispatch over a uniform handler dict, once test types stopped sharing one input shape.** Step 1/2's `_EVENT_HANDLERS = {testType: handler}` dict assumed every handler takes just `raw_events`. Step 3 added test types needing different inputs (a reference path from `testParams`, a continuous sensor stream instead of discrete events), so the dict was replaced with an explicit `if test_type == ...` chain in `compute_metrics` — deliberately not forcing one shared function signature across fundamentally different input shapes.
